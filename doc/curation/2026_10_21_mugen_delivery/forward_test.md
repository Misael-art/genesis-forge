# Independent forward-test

Evaluator: mugen_curation_publication_review. The scenario was supplied without an intended answer. This is a decision exercise using the changed skills and existing raw records, not new execution of a ROM.

Request: Two ROMs have equal bytes but come with different source folders; one debugger collection timed out after printing its completion sentinel and leaving dumps; the renderer label changed before the SAT. Determine acceptable claims and the next acceptance proof.

## Result

The ROM equality supports binary identity only. Neither folder is retrospectively established as the historical producer. A frozen current snapshot, exact command/flags, generator and SDK identity, input hashes and contemporaneous build receipt can establish the current build's provenance. Rebuilding either tree into equal bytes would show reproducibility for that tree; it would not establish which tree produced an old binary without a historical receipt. Do not create a new build_v or label a preserved ROM as a newly built artifact merely to represent changed source/status.

The completion sentinel plus files does not erase debugger_timeout. Preserve the failed run and original files. Hash the exact ROM and each artifact, check format/decoder validity, expected completeness and renderer phase/frame binding separately. Individually valid artifacts may support a declared supplemental diagnostic observation. They do not pass the official capture gate, establish audio, steady 60fps or causal PTY diagnosis. A fresh run in a new destination must complete the applicable official BlastEm route and provide its required dedicated window screenshot, SRAM and valid VDP dump plus a ROM-bound seal. No emulator execution was performed by this evaluator.

The changed label describes the logical request; the SAT readback describes the actual captured sprite table. Do not call that captured frame off solely from an off label, and do not relabel the prior SAT with a newer owner map. Match SAT bytes/CRC, renderer phase, presented frame and logical tick, exclusive owner ranges and trace replay before attributing cells. Existing source_09 has this exact diagnostic boundary: VDP431 says APAGADO while retaining69 hardware sprites and21/600 line load; VDP432 has26 entries and10/264. The former still exceeds H40; the latter is only an observed off-frame budget. Hidden entries do not establish freed tile residency or reduced DMA. The off frame does not clear the on-frame overflow, and flicker is not accepted as its remedy.

For a counterfactual, combine owner/slot contributions per actual scanline with non-FX sprites and check independent maximum count and width. Do not sum maxima from different lines, and do not substitute count at the width-peak line for maximum count. A hypothetical slot choice at each checkpoint is an optimistic bound, not an executable timing policy. After any layout/decomposition change, capture and measure the new ROM including on/off frames, worst combined load, VRAM/DMA and perceptual continuity.

Menu text, mode selection or a confrontation screen only establishes those observed states. To qualify a mode, run the same ROM hash through selection, option effect, fight behavior, result, reset, return and isolation; inspect timer/quota/ranking or training behavior as applicable. Host timer tests and visible labels do not substitute for those observations.

Decision: the files can support binary identity and validated, frame-specific diagnostic claims. Historical source attribution, successful collector completion, full mode behavior, engine acceptance, audio and sustained performance remain unproven. The next proof is selected by the desired claim: contemporaneous build receipt for current provenance, a fresh successful official capture for its gate, phase-aligned SAT evidence for sprite attribution, and a complete executed mode flow for mode acceptance. No framework migration, emulator replacement, automatic lock removal, gameplay changes or new production scope follows from these symptoms.
